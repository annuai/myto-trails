# M4 GPX and media pipeline Implementation Plan (condensed)

> Executed inline, test-first, one fresh whole-branch review at the end. Autonomous run: decisions are recorded as rulings in the final report.

**Goal:** Accept GPX and photo uploads safely, derive route data (distance, elevation, simplified line, profile), serve a sanitised GPX only for trails that may be downloaded, and show the route and elevation profile on trail pages.

**Spec:** docs/05 §8–9, docs/06 (route, gpx_file, media), docs/11 (uploads), docs/04 §3 (GPX flow), docs/12 M4, docs/14 §4 (export format).

## Decisions
- **Storage bytes:** the storage interface gains `get()`. A `local` provider (files under `.storage/`, HMAC-signed upload/download routes) makes the whole pipeline runnable without any cloud credentials; R2 and Supabase `get()` are implemented but unverified live.
- **Processing runs in the request** (GPX is light, images take about a second) behind a `processUpload` function that a job runner can call later. No background-job vendor is needed yet.
- **GPX is never served from storage directly.** The download route regenerates a plain GPX 1.1 from stored geometry and applies `canDownloadGpx`; originals stay private.
- **Sensitive trails** expose no route geometry and no GPX in M4 (reduced geometry is a later feature).
- **Images:** JPEG, PNG, WebP and AVIF in; WebP and AVIF variants out at 400/800/1200/1800 px (never upscaled); all metadata stripped; 40 MP limit. HEIC is not accepted (no libheif in the build).

## Global constraints
- GPX ≤ 5 MB, image ≤ 10 MB (`GPX_MAX_BYTES`, `IMAGE_MAX_BYTES`), ≥ 50 points or ≥ 500 m, ≤ 500 km, ≤ 10 minutes of processing time budget (soft), coordinates inside India's bounding box (outside = rejected with a clear message), no DOCTYPE/ENTITY in XML, no `<script>`-like content in names (names are escaped on output).
- Public coordinates in downloads are rounded to 5 decimals; stored precision 6.
- Uploads require a signed-in account; 30 upload requests per hour per user; object keys are generated UUIDs; every upload is re-checked with `verifyUpload` before processing.
- Errors shown to riders name the problem ("Only 1 track point found"); logs never contain file content.

## Tasks
1. Storage: `get()`, bytes in the memory provider, `local` provider with signed routes, contract tests.
2. GPX library: safe parse, validation, statistics, smoothing, simplification, profile, sanitised writer; hostile-file corpus tests.
3. Schema 0008: `upload`, `route`, `gpx_file`; nullable `media.revision_id`; public route/GPX views; duplicate-route search.
4. Image library: validate, strip, resize, variants, placeholder; tests with generated and hostile images.
5. Upload service: request, complete, process, status; DB tests.
6. Upload API routes (authenticated, rate limited) and local storage routes.
7. Public pages: route map, elevation profile (with table), GPX download route and interstitial; sample GPX data; import tool attaches GPX.
8. Verification and review.

## Review focus
1. Malicious GPX: XXE/billion laughs, huge/deep XML, NaN/Infinity, out-of-range coordinates, teleports, empty tracks, extreme point counts; limits enforced before heavy work.
2. Malicious images: decompression bombs, polyglots, wrong content type, EXIF/GPS leakage into variants.
3. Authorisation and gating: only the uploader reads their pending uploads; GPX only for published, downloadable trails; sensitive trails never expose geometry; the download route cannot be used to read arbitrary storage keys.
4. Local storage routes: signature, expiry, size and type binding, path traversal, overwrite.
5. Resource use: memory/time per request, rate limits, orphaned objects when processing fails.
